# 选题扩展 —— 交互设计流程上的支点

《智能设计系统与管理策略》2026 秋季 ｜ 版本 v0.2 ｜ 2026-10-15

> v0.1 从课程方法池出发；本版换一个视角：从**学生设计师的真实卡点**出发，沿交互设计流程寻找
> AI 可以作为「支点」的环节。课程方法池是参考，不是边界。

---

## 一、为什么换视角

v0.1 的推荐（启发式评审助手）属于「原型与评估」阶段。把这一阶段摊开看会发现：
**"评估"不是一件事，而是五种不同的评估对象**——评估什么，决定了选题的独特性和评测的客观度。
如果只做"通用启发式评审"，容易与其它小组同质；而只要换一个**更具体、可枚举**的评估对象，
立刻就有了别人没有的立足点。

同理，"直接帮设计师做产出"这条路，也可以按产出物的类型切开：内容（文案）、动态（动效）、
系统（规范与 token）、结构（信息架构与原型）。

---

## 二、流程支点地图

| 阶段 | 可用支点 | 说明 |
| --- | --- | --- |
| ① 情境与需求 | （本次不展开） | 主要依赖访谈与调研，已在 v0.1 覆盖 |
| ② 概念与结构 | 信息架构 / 交互模式参考库 | 与「亲和图」有重叠，优先级低 |
| ③ 界面产出 | **文案生成 · 动效规格 · 规范文档** | 学生最缺支持、产出立即可用 |
| ④ 原型与评审 | **状态审查 · 无障碍审查 · 一致性审查 · 设计批评 · 测试方案** | 痛点最真、评测最可量化 |
| ⑤ 交付与迭代 | 交付规范检查（Figma 版） | 工程味重，方法论锚点偏弱 |

两处最值得投入的支点：**④ 原型与评审**（用户偏好）和 **③ 界面产出**（可直接分担工作）。

---

## 三、评估类：五个切面

同样是"审查一个设计稿"，评估对象不同，选题的技术路线、评测难度和差异化程度完全不同。

| 切面 | 评估对象 | 正确性标准 | 评测客观度 | 难度 | 推荐 |
| --- | --- | --- | --- | --- | --- |
| **A 状态完整性** | 组件状态空间是否闭环 | 状态可枚举，可对照清单 | 高 | ★★ | ★★★★★ |
| **B 无障碍与可读性** | 对比度 / 字号 / 语义 / 色彩依赖 | WCAG 有明确阈值 | 高（可精确验证） | ★★ | ★★★★ |
| **C 设计一致性** | 颜色 / 字号 / 间距 / 圆角是否漂移 | 数值可精确比对 | 高 | ★★ | ★★★★ |
| D 设计批评 | 方案质量与思考深度 | 无标准答案，靠专家判断 | 低（需行为指标补） | ★ | ★★★ |
| E 测试方案生成 | 测试设计是否覆盖关键任务 | 与标准流程对照 | 中 | ★ | ★★ |

评测客观度非常关键：它直接决定第 6 周测试报告能否写出"硬"结论。
A / B / C 三个切面都有客观分母，D / E 则需要用行为指标（改动量、命中率）来替代。

### 切面 A · 界面状态与文案助手（重点推荐）

**一句话**：进是设计稿，出是「状态矩阵 + 全套文案」。

- **方法论锚点**：启发式评估中「错误预防」「帮助用户识别、诊断与恢复」两条原则的具体化；
  状态完整性本身就是资深设计师检查新人的第一道关。
- **痛点**：空态 / 加载 / 错误 / 边界数据 / 权限不足最容易被漏；文案全是占位符，语气与场景对不上；
  改稿时状态清单靠脑子记，越改越漏。
- **Skill 流水线**：设计稿截图 → 组件与数据依赖识别 → 状态空间枚举 → 缺口清单 + 优先级 → 各状态文案生成。
- **人机协同节点**：确认状态适用性（标记 NA）、语气与比喻定调、文案改写定稿、复审闭环。
- **API 候选**：`/api/state-audit`（状态矩阵 + 缺口清单，结构化 JSON）、
  `/api/copy-suggest`（按状态生成多组文案，含语气选项）。
- **测试评估**：
  - 信度：与 3 位高年级 / 从业设计师的人工审查对照 —— 状态召回率、误报率；
  - 效率：人工自查 30 分钟 → 工具 3 分钟；
  - 有用性：A/B 小实验 —— AI 文案版 vs 占位文案版原型的任务理解测试（理解正确率 / 完成时间）。
- **差异化**：状态的正确性标准是"可枚举"的，评测有客观分母；"审查 → 生成 → 复审"闭环完整，
  人机协同节点密集，正好对课程重点。
- **演进**：v1 状态审查 → v2 文案生成 → v3 并入「设计稿体检」复合技能。

### 切面 B · 无障碍与可读性审查

**一句话**：确定性计算做底盘，AI 判断做增量 —— 一个"可信度分层"的审查工具。

- **方法论锚点**：WCAG 无障碍标准 + 包容性设计方法。
- **技术架构（本选题最大亮点）**：
  - 确定性层（可精确计算 / 有标准阈值）：对比度、字号、点击目标尺寸、行距；
  - AI 层（需要语义判断）：图标含义是否清晰、是否只靠颜色传达信息、错误提示是否可操作、认知负荷。
- **痛点**：对比度、字号不达标肉眼看不出来；色彩是唯一信息载体；
  不懂标准条款，改也不知道改到哪一档。
- **Skill 流水线**：截图 / HTML / 设计稿 → 前景背景色提取 → WCAG 阈值计算 → AI 语义审查 → 分级问题清单 + 依据引用。
- **人机协同节点**：色值人工确认（兜底）、品牌色例外判定、严重度校准、修复建议采纳。
- **API 候选**：`/api/contrast-check`（确定性计算，可独立复用）、`/api/a11y-audit`（综合审查）。
- **测试评估**：对比度模块与 axe DevTools / Lighthouse 对照（客观可验证）；语义类问题与专家组评吻合度；
  单稿审查时间对比。
- **差异化**：报告里能写出"哪些结论可信、为什么"的深度；国内信息无障碍政策背景也让选题有现实意义。

### 切面 C · 设计一致性审查

**一句话**：让"你有 9 种蓝色"这件事，被一眼看见。

- **方法论锚点**：设计系统审核（design system audit）。
- **痛点**：多页设计后颜色 / 字号 / 间距悄悄漂移；同一种按钮出现 5 种圆角，说不上哪个是标准；
  手工盘点是体力活，没人愿意做。
- **Skill 流水线**：多页截图 → 色板与尺寸提取 → 近似值聚类 → 漂移点清单 → 合并建议 + token 表。
- **人机协同节点**：区分"刻意差异"与"误用"、合并决策、token 命名、纳入规范。
- **API 候选**：`/api/palette-extract`、`/api/drift-report`。
- **测试评估**：与人工盘点对照（色值数量、误报率，可精确验证）；盘点时间对比；
  产出的 token 表能否直接进入后续项目。
- **差异化**：数值比对完全客观；报告本身就是设计系统的起点，演示冲击力强。

### 切面 D · 设计批评辅助（苏格拉底式）

**一句话**：不给答案，只提问 —— 从多视角向你的方案发问。

- **方法论锚点**：设计批评（critique）流程：描述 → 分析 → 解释 → 判断；对应课程中的"激发模式"。
- **痛点**：学生缺反馈循环；同学意见零散，老师意见太温和。
- **产出**：多视角问题清单（用户 / 业务 / 技术 / 伦理）+ 优先讨论议题 + 答辩预演问题。
- **测试评估**：与教师评语对照（议题覆盖率）；学生改动量、答辩问题命中率等行为指标。
- **风险**：评测偏主观，需要用行为指标补充，否则第 6 周报告难写。

### 切面 E · 可用性测试方案生成

**一句话**：生成任务脚本、观察点、成功标准，测试后自动出报告。

- **痛点**：学生不会组织可用性测试，方案设计本身就需要经验。
- **测试评估**：与手动设计方案对照；测试主持人时间节省；报告质量评分。
- **风险**：AI 只负责"生成文本方案"，技术含量偏低，容易被其它小组覆盖。

## 四、产出与交付类：四个切面

这类选题的价值主张是"直接分担工作"，评估方式要落在**产出物的可用性**上。

| 选题 | 产出 | 难度 | 评测方式 |
| --- | --- | --- | --- |
| 界面文案生成与语气检查 | 各状态文案表 + 语气规范 | ★ | A/B 理解测试、人工撰写对照 |
| 微交互 / 动效规格生成 | 动效规格卡 + 参数预览 + 代码片段 | ★★ | 与资深设计师 / 开发者的规格对照；可实现性评分 |
| 设计规范文档生成 | 可交付的组件规范文档 | ★★ | 开发者阅读后实现正确率 |
| 交付规范检查（Figma 版） | 图层 / 变量 / 库组件使用检查报告 | ★★ | 人工检查对照、修复前后对比 |
| 交互模式参考库 | 模式卡片（场景 / 优缺点 / 陷阱） | ★ | 方案质量提升、查找时间 |

**动效规格生成**值得单独说一句：学生"说不清动效"是交付环节的常见断点，
而规格卡（触发 / 时长 / 缓动 / 位移 / 中断规则）是具体、可评审、可现场调参的产出物，
演示效果好；风险在于"好动效"标准模糊，需要用"参数规范符合度 + 开发者评审"来量化。

**交付规范检查（Figma 版）** 的独特优势：可以直接读取 Figma 文件结构（图层命名、变量绑定、
库组件使用情况），"选中页面 → 一键体检"的演示效果极佳；但它的方法论锚点偏工程规范，
如果在意与课程"设计研究方法"的贴合度，需要额外论证。

## 五、推荐与演进路线

### 推荐排序

1. **A · 界面状态与文案助手**（首选）—— 痛点最真、评测最客观、闭环最完整；
   学生交稿前真的会用一次，作品集里也拿得出手。
2. **B · 无障碍与可读性审查**（架构最漂亮）—— "确定性 + AI 分层"让工具可信且可解释，
   测试报告能同时给出客观分母与专家对照；有政策与伦理叙事。
3. **C · 设计一致性审查**（数据最客观、演示最直观）—— 产出直接是设计系统的起点。

### 演进路线（写进设计文档的加分项）

```
v1  单点切入       状态审查（状态矩阵 + 缺口清单）
v2  审查 → 产出     加入文案生成，形成"审查 → 生成 → 复审"闭环
v3  复合技能        并入无障碍审查、一致性审查 →「设计稿体检」一键报告
```

课程建议"优先完成一个流程技能，并在文档中说明如何扩展为复合技能"——这条路线正好对上。

### 与 v0.1 的关系

v0.1 的「启发式评审助手」与切面 A 本质同源：状态审查是它最锐利、最可验证的切面。
**建议二选一**，把精力放在一个切入点上；若选 A，则在文档中说明通用启发式评审是 v3 的扩展方向。
