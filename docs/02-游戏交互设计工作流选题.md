# 选题扩展 v0.3 —— 游戏交互设计工作流

《智能设计系统与管理策略》2026 秋季 ｜ 版本 v0.3 ｜ 2026-10-15

> 前两版从"设计研究方法"和"通用交互设计流程"出发；本版基于游戏交互设计师的真实工作流：
> **策划案 → 交互稿 → GUI 视觉稿 → 三方审核 → Unity 落地 → 程序实现**。
> 沿这条链找支点：哪里阻力最大，哪里就是选题。

---

## 一、把工作流摊开：五个交接边界 + 一个贯穿缺口

| 边界 | 交接内容 | 典型风险 |
| --- | --- | --- |
| ① 策划 → 交互 | 策划案（玩法 / 数值 / 系统） | 需求理解偏差；UI 相关信息缺失，来回追问 |
| ② 交互 → GUI | 交互文档（结构 / 状态 / 标注） | 标注不全；GUI 不知道约束与优先级，返工 |
| ③ 三方审核 | 视觉稿（策划 + 交互 + GUI 共同评审） | 意见散乱、重复、互相冲突；轮次多 |
| ④ 审核 → Unity | 切图 / 组件 / 适配规则 | 落地时才发现设计不可实现 |
| ⑤ 程序实现 | 实现与设计稿的差异 | 验收标准不统一 |
| **贯穿缺口** | **交互稿自查自检** | **不确定是不是"为了设计而设计"；抽象理论落不到具体界面决策上** |

前五个边界是**协作问题**（信息在人际之间丢失或变形），贯穿缺口是**质量问题**（信息在自己手里没被检验）。
两者都能做选题，但对课程的价值不同：协作类评测更客观，质量类更接近设计研究的内核。

## 二、五个交接点 + 自查缺口的选题映射

| 位置 | 选题方向 | 评测抓手 | 推荐 |
| --- | --- | --- | --- |
| ① 策划 → 交互 | 策划案拆解助手（需求清单 + 待澄清问题清单） | 信息项召回率、有效问题率 | ★★★ |
| ② 交互 → GUI | 交互稿交付体检（Handoff Checker） | 检查项覆盖率、返工原因对照 | ★★★★ |
| ③ 三方审核 | 评审意见聚合与冲突检测 | 意见召回、会议时间节省 | ★★ |
| ④ Unity 落地 | （并入交付体检的"落地约束"模块） | 适配问题提前发现数 | — |
| 缺口 · 质量 | **目标驱动的设计自查** | 判据覆盖度、问题命中率、采纳率 | ★★★★★ |
| 缺口 · 质量 | **瞬间可读性与注意力审查** | **瞬时识别实验（效度验证）** | ★★★★★ |
| 延伸 | 跨系统交互一致性审查 / 手柄焦点流可达性 | 一致性盘点、可达性形式化验证 | ★★ |

## 三、三个重点候选

### 候选 ① 目标驱动的设计自查（首选）

**一句话**：把"为了设计而设计"变成可检验的问题 —— 目标 → 判据 → 检查。

**它解决的问题**（正是"不知道如何从抽象理论过渡到交互设计"）：

- 自查靠感觉，无法判断设计是否真的服务目标；
- 对齐、对比、间距这些基础掌握后，不知道下一层该看什么（信息层级、认知负荷、注意力和决策成本）；
- 评审意见零散，改完不知道有没有变好。

**Skill 设计**

- 输入：设计目标（策划意图，一段自然语言）+ 交互稿截图 + 界面类型（战斗 HUD / 背包 / 商店 / 任务 / 结算）；
- 处理：
  1. **目标结构化**：把"要爽""要清晰""要有代入感"这类模糊目标拆成可检验判据
     （如"清晰" → 关键信息 0.5 秒内可辨识；"有代入感" → 战斗 HUD 最小化、非战斗信息后置）；
  2. **判据库匹配**：从判据库（信息层级 / 认知负荷 / 反馈循环 / 决策成本 / 一致性）挑选适用项；
  3. **逐条检查**：对照设计稿给出证据（引用具体区域）、通过 / 存疑 / 未通过；
  4. **输出改动建议**：每条建议标注依据的判据与理论。
- 输出：对齐度报告（偏离项 + 改动建议 + 理论依据）+ 待讨论清单。
- **人机协同**：确认目标表述（AI 复述 → 设计师纠正）→ 确认判据适用性 → 标注"已解决 / 待讨论" → 复审闭环。
- **API 候选**：`/api/objective-to-criteria`（目标 → 判据清单）、`/api/design-check`（判据 → 检查报告）。

**测试评估**

- 信度：与资深交互设计师手写的判据对照（覆盖度、可用性评分）；
- 效率：自查时间对比；
- 有用性：用"已知问题"样本集验证命中率 + 设计师建议采纳率。

**为什么推荐**：它是唯一一个**把设计理论到实践的翻译过程本身做成工具**的选题 —— 做这个项目的过程，
就是你把认知负荷、信息层级、反馈循环这些理论真正内化的过程。评审时也是最有故事可讲的方向。

**风险与对策**：评测偏主观 → 用"已知问题样本集 + 采纳率"两个行为指标兜底；
判据库的领域知识需要自己搭 → 这本身就是可以写进最终报告的研究贡献。

### 候选 ② 瞬间可读性与注意力审查（评测最硬）

**一句话**：高压场景里，玩家能在 0.5 秒内抓到关键信息吗？

**它解决的问题**：战斗、结算这类高压场景对界面有"瞬间可读"的要求 ——
关键信息（血量、技能冷却、弹药、目标状态）必须在极短时间内可辨识。
但平时做设计看不出问题：信息密度过高、依赖颜色单一编码、关键信息不在视线焦点、
与伤害数字 / 特效争夺注意力；改版后也只能凭感觉说"好像清楚点了"。

**Skill 设计**

- 输入：游戏截图 / 战斗片段（可批量）；
- 处理：
  1. 结构层：信息密度、分组、视觉层级诊断；
  2. 视觉层：关键元素的大小、位置、与视线焦点的关系；
  3. AI 层：语义重要性判断（哪些是"关键信息"）+ 干扰源识别；
- 输出：可读性风险清单（按优先级）+ 改版建议 + 改版前后对比。
- **人机协同**：设计师标注关键信息清单（AI 建议 + 人工确认）、风险点确认 / 驳回、改版前后对比复核。
- **API 候选**：`/api/glanceability-audit`、`/api/attention-map`。

**测试评估（本选题的杀手锏）**

- 信度：与资深设计师人工审查对照；
- **效度：瞬时识别实验** —— 向被试展示界面 300ms 后，测其识别关键信息的准确率与反应时间；
  比较"工具判定高风险"与"低风险"的版本，验证工具预测与真人表现的相关性。
  这是一个真正的"工具预测 → 实验验证"闭环，测试报告的分量远超同类作业；
- 效率：审查时间对比。

**风险与对策**：需要构造素材与招募被试（班里同学即可，8–12 人小样本足够做出趋势）。

### 候选 ③ 交互稿交付体检（最实用、最客观）

**一句话**：在交给 GUI 和 Unity 之前，把该标的都标清楚。

**它解决的问题**：把"交互 → GUI → Unity"链路上反复出现的返工原因固化成检查项。

**检查项清单（示例）**

- 状态标注是否完整（默认 / 悬停 / 禁用 / 冷却 / 选中 / 等级不足）；
- 文本容量上限与多语言膨胀余量（英文 / 俄语通常膨胀 30–50%）；
- 适配约束（安全区、16:9 / 21:9 / 刘海屏）；
- 九宫格与切图规则、动效意图（触发 / 时长 / 缓动）、焦点顺序与按键提示、命名规范。

**Skill 设计**

- 输入：交互文档 / 设计稿（Figma 或截图）+ 目标平台；
- 输出：缺失项清单（按角色分组：给 GUI 的 / 给程序的）+ 优先级 + 补齐建议；
- **人机协同**：确认项目豁免项、补充团队规范、分工指派、复审闭环；
- **API 候选**：`/api/handoff-lint`、`/api/adapt-check`（适配与多语言膨胀预检）。

**测试评估**：与 GUI / 程序侧的历史返工原因对照（客观）；交付前检查时间 vs 后续返工时间；
GUI / 程序侧返工次数变化。

**为什么它好**：检查项可枚举 → 评测完全客观；做的过程会把团队踩过的坑整理成规范库。

## 四、补充方向速览

| 选题 | 产出 | 评测抓手 | 难度 |
| --- | --- | --- | --- |
| 策划案拆解助手 | UI 需求清单 + 信息项 + **待澄清问题清单** | 信息项召回率、有效问题率 | ★★ |
| 评审意见聚合与冲突检测 | 按角色分类的意见清单 + 冲突检测 + 追踪 | 意见召回、会议时间节省 | ★★ |
| 跨系统交互一致性审查 | 背包 / 商店 / 技能等系统的模式一致性报告 | 与人工盘点对照 | ★★ |
| 手柄焦点流可达性审查 | 焦点顺序可达性报告（图论可达性） | 可达性可形式化验证 | ★★ |

其中"策划案拆解助手"的亮点是**主动生成需要向策划澄清的问题清单** —— 把"来回追问"变成一次性的、
结构化的沟通，直接减少交接起点的时间损耗。

## 五、推荐与组合路线

### 排序

1. **目标驱动的设计自查** —— 直击"为了设计而设计"，把设计理论落地成判据；个人成长价值最高。
2. **瞬间可读性与注意力审查** —— 评测最硬：工具预测 + 真人实验对照，测试报告有真正的效度验证。
3. **交互稿交付体检** —— 最实用、最客观：检查项可枚举，交接阻力直接下降。

### 组合路线（可写进设计文档）

```
v1  目标驱动的设计自查        判据 → 检查报告（管"设计对不对"）
v2  加入瞬时识别实验模块      工具预测 → 真人验证（管"能不能被验证"）
v3  并入交付体检             「交互稿上线前体检」：质量 + 交付双重检查（管"能不能落地"）
```

三者的关系：**① 管设计对不对，② 管能不能被验证，③ 管交出去能不能落地** —— 按 v1/v2/v3 串成一条线，
正好对应课程"优先完成流程技能，再扩展为复合技能"的建议。

### 与前两版的关系

- v0.2 的「状态完整性审查」在游戏场景里只会更复杂（技能冷却、等级不足、断线重连……），
  可作为候选 ③ 交付体检的一个模块，或独立成题；
- v0.1 的「启发式评审助手」在游戏语境下建议改造为候选 ②（瞬间可读性），因为通用启发式原则
  对游戏界面的解释力有限，而"高压场景下的信息可读性"才是游戏特有的真问题。
