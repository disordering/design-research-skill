## 为什么合并（原方案 A + B）

两个方向本质是同一件事的两个切面：**都是用外部标准检验设计稿** ——
一个是权威**规范**的标准，一个是真实**玩家**的标准。合并后：

- 共用同一条流水线与同一套人机协同节点，实现量增加有限；
- 测试报告可以同时给出三类证据：**信度**（与专家对照）、**效度**（与真人实验对照）、**溯源率**（结论带规范依据的比例），比单一功能的工具扎实得多；
- 团队分工天然：2 人做检查 A、2 人做检查 B，最后合成一份报告。

## 分层结构

| 层 | 内容 | 检验标准 |
| --- | --- | --- |
| 检查 A · 规范对齐 | 设计目标结构化 → 从规范库（Apple HIG 等）检索判据 → 逐条检查 | 权威规范（可溯源） |
| 检查 B · 可读性与注意力 | 高压场景（战斗 / 结算）的信息密度、视觉层级、视线焦点、干扰源 | 真实玩家（可实验验证） |
| 人机协同（贯穿） | 确认目标表述 · 确认 / 驳回发现 · 严重度校准 · 复审闭环 | 研究者判断 |
| 验证（加分模块） | 关键页面做瞬时识别实验（300ms 展示 → 识别准确率） | 工具预测 vs 真人表现 |

## 机制 · 流水线

```
交互稿 / 截图 → 目标结构化 → 规范库检索 → 两类检查 → 分层审查报告
```

报告内容：问题清单（分层 + 优先级）+ 证据（引用界面区域）+ 依据（引用规范条款）+ 改动建议 + 待讨论清单。

## 人机协同节点

- 确认目标表述（AI 复述 → 研究者纠正）；
- 确认 / 驳回每一条 AI 发现，校准严重度；
- 标注「已解决 / 待讨论」→ 复审闭环；
- 规范库维护：团队可以补充自己的项目规范（工具的知识是可扩展的）。

## API 候选

- `/api/criteria-check`：目标 + 规范 → 判据检查清单（含依据引用）
- `/api/glanceability-audit`：可读性与注意力风险清单

## 测试评估方案

| 指标 | 做法 |
| --- | --- |
| 信度 | 与 2 位资深设计师的人工审查对照：问题召回率 / 误报率 |
| 效度 | 瞬时识别实验：工具判定的高风险 vs 低风险页面，真人识别准确率是否有差异 |
| 溯源与效率 | 结论中带规范依据的比例（特色指标）；单稿审查时间对比（小时 → 分钟） |
| 有用性 | 设计师试用评分 + 建议采纳率 |

## 8 周落地路线

```
v1（第 4 周 MVP）  检查 A：目标结构化 + 规范检索 + 报告，先聚焦一类页面（任务面板 / 背包）
v2（第 5–6 周）    加入检查 B 的可读性模块；第 6 周测试报告（含瞬时识别实验）
v3（第 7–8 周）    汇总为一份「设计体检」报告 + API 封装 + 演示
```

## 关键决策与风险

- **规范库分层**：通用规范（Apple HIG、Material）+ 平台指南（主机 / 手游）+ 团队规范；
  每条依据标注来源与适用范围，避免"拿移动端规范审主机界面"。
- **场景收敛**：v1 只做一类页面，不做全量界面；报告先做结构，后做美化。
- **实验成本**：被试用班里同学，8–12 人小样本即可做出趋势。
