# 最终方案 · 交互设计评审助手（泛用）

《智能设计系统与管理策略》2026 秋季 ｜ 2026-10-15

> 这份是结论。`docs/00`–`02` 是探索记录，无需细读。
> Figma 对应页面：`选题`（总览 → 同类产品参考 → 开源 Skill 参考 → Insight → 详情），其余页面已归档。

**一句话**：把**启发式评审**重构为「多维度判据 + 可溯源结论 + 可实验验证」的评审工具。
**不押注单一品类**：网站 / APP / 游戏共用同一套框架，换判据库就换品类。

---

## 从 7 个案例（3 个商业产品 + 4 个开源 Skill）得到的三个判断

1. **判据要有出处** —— 商业产品（UX Audit AI、Heustrics）只给结论与评分，不给出处；开源 Skill 反过来，
   把原则与官方规范写成判据（M3 要求先核对官方指南、design_skill 要求引用 WCAG 条款）。
   → 每条结论挂上判据 / 规范条款，这是现成的差异化空位。
2. **审查链要走完** —— 课件给的是「原则 → 检测 → 描述 → 建议」；产品大多停在检测与描述，
   开源 Skill 有建议但没有检测能力（它们只读代码）。
   → 把四段式做完整：每条问题都带证据（界面区域）+ 描述 + 可执行建议。
3. **判断要能被验证** —— 没有同类产品验证自己的判断：Attention Insight 只给热图，Heustrics 用合成用户当证据。
   → 用真人小实验做效度验证（工具判高风险 vs 低风险，看真人表现差异），正好对应课程的信效度要求。

## 技术路径（把课件里的手段串成一条链）

```
界面输入（截图 / 原型 / 线上页面）
  → 多模态视觉理解（GPT-4V / Claude Vision）
  → UI 元素检测与识别
  → 判据知识库检索（HIG / Material / WCAG / 平台指南）
  → LLM 评审
  → 意见生成（原则 → 检测 → 描述 → 建议）
  → 人工复核
  → 版本差异对比
```

分工：多模态视觉理解负责「看懂界面」；知识库负责「拿什么判据」；UI 元素检测让建议落到具体控件；
版本对比回答「改完变好了吗」。

## 一、为什么是"启发式评审的升级版"

前三版分别探索了「规范对齐」「状态与可读性」「交接检查」等切面，共同的问题是把方法拆得太细。
回到课程方法池里的原方法 —— **启发式评估（Heuristic Evaluation）** —— 它本身就是"专家按一组原则逐条检查界面"，
我们要做的是把这个方法重构：**判据从单一原则扩展为多维判据，结论从主观描述升级为可溯源证据，判断从可信度存疑升级为可实验验证**。

## 二、三层判据（这是选题的核心）

| 层 | 判据来源 | 检验什么 |
| --- | --- | --- |
| ① 通用交互原则 | 尼尔森十大启发式等跨端原则（错误预防、反馈、一致性、容错） | 界面是否"好用、不出错"（网站 / APP / 游戏通用） |
| ② 平台规范符合度 | 平台 / 设计系统规范：Apple HIG、Material、WCAG、游戏平台指南、团队设计系统（**"喂 apple.com"就落在这里**） | 是否符合既定标准，**可溯源**（按品类切换） |
| ③ 场景专项 | 由品类决定：网站看信息架构与表单，APP 看手势与状态，游戏看高压可读性与注意力 | 在真实使用场景里是否真的可用，**可实验验证** |

每条结论 = **证据锚点**（引用界面区域）+ **判据来源**（引用条款或原则）+ **严重度分级**。
第 ②③ 层即「品类可配置层」：同一套框架与流水线，换判据库就能从网站切到 APP、切到游戏。

## 三、机制 · 流水线

```
输入 → 视觉理解与元素识别 → 判据库匹配（三层）→ LLM 逐条评审 → 意见生成（原则 → 检测 → 描述 → 建议）
     → 人工复核 → 版本差异对比 → 分级评审报告 + 待讨论清单
```

输入形式支持三种：**设计稿截图**（任何品类都能用，v1 起步）、**可交互原型**、**线上页面**（网站 / APP）。

## 四、人机协同节点

- 确认设计目标与适用判据（AI 复述 → 研究者纠正 / 增删）；
- 确认 / 驳回每一条 AI 发现，校准严重度；
- 标注「已解决 / 待讨论」→ 复审闭环；
- 判据库维护：团队可补充自己的项目规范与经验（工具的知识是可扩展的）。

## 五、API 候选

- `/api/review-audit`：截图 + 判据 → 分级问题清单（含证据与依据引用）
- `/api/glanceability-audit`：场景专项 —— 可读性与注意力风险清单

## 六、测试评估方案

| 指标 | 做法 |
| --- | --- |
| 信度 | 与 2 位资深设计师的人工评审对照：问题召回率 / 误报率 |
| 效度 | 瞬时识别实验：工具判定高风险 vs 低风险的页面，真人识别准确率是否有差异 |
| 溯源率 | 结论中带判据 / 规范依据的比例（特色指标） |
| 效率与有用性 | 单稿评审时间对比（小时 → 分钟）；设计师试用评分 + 建议采纳率 |

## 七、市场对照：已经有什么，我们站在哪（2026-10 调研）

| 类别 | 代表 | 它们做什么 | 缺口 |
| --- | --- | --- | --- |
| AI 启发式评估工具 | uxaudit.tech、heustrics.com、HeuriLens、Heurator（Figma 插件）、Figma 社区「heuristic-evaluation-with-ai」 | 上传界面/链接 → 自动生成启发式问题清单 | 面向 Web/App；结论不溯源；无实验验证 |
| 设计规范类 Agent Skill | gnurio/refactoring-ui-plugin（★445）、skydashnet/material-design-3-ui-skill（★148）、grapeot/design_skill | 把设计原则 / 设计系统变成 AI 评审技能 | 面向代码与实现层；绑定单一设计系统；不针对游戏 |
| 注意力预测工具 | Attention Insight、EyeQuant | 预测视觉注意力热图 | 只给热图，不给评审结论与改版建议 |
| 可用性测试平台 | Maze、Lyssna、Uxia | 组织测试、收集与分析数据 | 依赖真人被试与周期；不做设计稿审查 |
| 品类化 AI 评审（含游戏） | **未发现成熟工具** | — | **空位** |

**我们的位置**：交互设计（网站 / APP / 游戏通用）× 三层判据 × 每条结论可溯源 × 关键判断可被真人实验验证。
（同类都集中在 Web/App 与代码评审；「通用原则 + 平台规范 + 场景专项」三层叠加 + 实验验证的组合没有现成产品。）

### 同类产品的技术路径（2026-10 实测）

| 路线 | 代表 | 怎么做 | 局限 |
| --- | --- | --- | --- |
| A · 实时页面分析 | UX Audit AI（uxaudit.tech） | 输入实时 URL → 抓取渲染 → 模型分析 → UX / Accessibility 评分 + 界面区域高亮的问题卡 | Web 专用；不引用规范条款；无人工或实验验证 |
| B · 合成用户测试 | Heustrics（heustrics.com） | 爬取应用 → 生成多个用户画像（persona）→ 在浏览器里跑任务 → 带证据的评分报告 | 仍限 Web/App；依赖爬取与自动化可行性；不做设计稿审查 |
| C · 专用预测模型 | Attention Insight | 基于眼动数据训练的显著性模型 → 预测视觉注意力热图 | 只给热图，不给评审结论与改版建议 |
| D · 原则 / 规范类 Agent Skill | refactoring-ui-plugin、material-design-3-ui-skill、design_skill、ai-friendly-web-design-skill | 把设计原则或设计系统文档写成结构化 SKILL.md，让 Agent 按判据评审界面或代码 | 面向代码与实现层；绑定单一设计体系；不做实验验证 |
| E · 官方设计插件 | Anthropic `knowledge-work-plugins`（Design Plugin） | 设计批评 / 交付 / 无障碍 / UX 文案 / 设计系统审计 / 研究综合 | 通用设计工作流；面向代码与已实现界面；不涉及实验验证 |

**三条启示**：

1. **判据要有出处**：`design_skill` 明确提出"确定性工具给事实，模型给判断"，并要求无障碍结论引用 WCAG 条款 —— 说明"判据溯源"是正确方向，也是我们的差异化。
2. **不必重复造轮子**：通用原则类评审已有成熟实现，`refactoring-ui-plugin` 的 10 个原子技能（层次 / 字体 / 配色 / 间距 / 按钮层级 / 杂乱 / 空态 / 阴影 / 对比度 / 分组）的判据结构可直接借鉴。
3. **空位确认**：品类化判据（网站 / APP / 游戏可切换）+ 规范溯源 + 真人实验验证，没有现成产品。

**本地资料**：下载的开源 skill 在 `reference/skills/`，同类产品截图在 `reference/screenshots/`（均不随仓库交付）。
Figma `选题` 页中对应「参考 · 同类产品界面」（3 个产品页截图）与「参考 · 开源 Skill」（4 个仓库页截图 + 借鉴点）。

## 八、8 周落地路线

```
v1（第 4 周 MVP）  截图输入 + ① 通用交互原则 → 四段式意见，先跑通一条链
v2（第 5–6 周）    接入规范知识库（可溯源）+ UI 元素检测（建议落到控件）；第 6 周测试报告（含真人小实验）
v3（第 7–8 周）    版本差异对比 + 品类判据库可配置 + API 封装 + 演示视频
```

## 九、关键决策与风险

- **判据库分层**：每条依据标注来源与适用范围（避免"拿移动端规范审主机界面"）；
  用爬取 / 整理好的规范文档做语料库（Apple HIG 等），检索 + 引用。
- **品类收敛**：v1 只跑通一条链（截图 + 通用原则），品类切换放在 v3，避免一开始就贪大。
- **实验成本**：被试用班里同学，8–12 人小样本即可做出趋势。
