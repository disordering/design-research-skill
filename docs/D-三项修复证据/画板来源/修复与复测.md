# 画板快照按文件和节点核对来源

同一组快照跑了两次。修复前，三次读取各生成一条设计证据，其中两条指向错误来源。修复后，只有文件 A 的节点 1:1 生成证据。两种错误请求各返回明确的来源错误。[修前返回](修前.json) · [修后返回](修后.json)

| 请求 | 修前 | 修后 |
| --- | --- | --- |
| 文件 A，节点 1:1，清单、元数据、截图齐全 | 成功，1 条带截图的证据 | 成功，1 条带截图的证据，各字段与修前一致 |
| 文件 B，节点也叫 1:1，归档实际来自 A | 成功，把 A 的截图登记在 B 下 | 读取失败，报告文件键不匹配，证据 0 条 |
| 文件 A，请求 9:9，清单中没有这个节点 | 部分读取，生成一条带“已验证”标志的节点记录 | 读取失败，报告节点未登记，证据 0 条 |

运行使用上次的复现脚本、40 × 28 像素的蓝色测试图和同一组文件键、节点号。修前结果与上次留档逐字段一致。测试经过实际会话入口和证据存储，在模型调用前结束。[原复现脚本](../../D-续测证据/批次/快照来源复现.py) · [上次留档](../../D-续测证据/批次/快照来源实测.json)

适配器现在先核对清单文件键、节点登记和归档内容。存在 XML 时再核对其中的根节点编号。清单内只存截图的子节点仍能看图，只存 XML 的节点仍能提供结构证据。切换画板、快照、起点或版本后，系统重新建立可继续检查的子节点列表。旧快照若缺文件键或目标节点登记，需要补齐真实来源才能用于评审。[产品实现](../../../engine/session_adapters.py)

## 用原批次的 11 张图复跑

从上轮材料索引取出 T07 护法 4 张和 T08 吴山石 7 张归档 JPEG。逐张核对索引 SHA-256、组内文件键和节点号。把 JPEG 解码出的 RGB 原像素无损存为 PNG，按快照约定放入临时目录。修前适配器从项目提交 `ec17fea` 载入，修后使用本地产品代码，两组共享同一份快照与测试条件。每次读取经产品会话入口，并从该会话磁盘存储取回证据逐像素比较。此轮走的是本地归档读取路径。[原批次材料索引](../../D-续测证据/批次/材料索引.json) · [11 图复跑脚本](11图同材料复跑.py)

| 23 个请求，修前修后各跑一遍 | 修前 | 修后 |
| --- | --- | --- |
| 请求组内文件，节点正确 | 11/11 返回图片，像素与原图一致 | 11/11 返回图片，像素与原图一致 |
| 只把请求文件键换掉，保留各自节点号 | 11/11 仍取得原文件的图片并标为已验证 | 11/11 拒绝错文件，证据总数 0 |
| 正确文件，请求清单外的节点 | 1 条部分证据，被标为已验证 | 返回节点未登记，证据总数 0 |

46 个会话的来源、节点、错误码、存储图与原像素指纹均在原始记录中。11 次正确输入的尺寸、PNG 字节及解码后像素在两个版本中全部一致。[11 图逐项结果](11图同材料结果.json)

另实测了一种错图路径。在 Windows 将 A 快照的图片目录联接到相邻 B 快照，两个归档使用同号节点。加入路径核对前，A 的清单会让 B 的 75 字节图片通过。修复后，系统识别出目录重定向，在读取图片前返回来源错误。离线快照现在要求清单、元数据与图片放在对应快照的实际目录。[重定向修前](目录重定向修前.json) · [重定向修后](目录重定向修后.json)

适配器测试 27 项全部通过。新增 7 项覆盖错文件、缺文件键、节点未登记、只有清单没有归档内容、XML 根节点不符、切换起点后继续访问旧子节点、图片目录指向其他快照。[测试代码](../../../tests/test_session_adapters.py) · [逐项运行结果](适配器回归.xml)
