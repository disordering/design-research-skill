## 已确认的触发与影响

`engine/session_service.py` 中 `_apply_check_plan` 约第 1670 行，在本轮已有同一 `ref` 的已判断覆盖项、后续规划新增另一个 `coverage_id` 时，用 `template.model_copy(deep=True)` 复制旧项，只先改 `check_id`。其后写入新覆盖标题、任务、来源及规划字段，没有清空旧判断。

因此新覆盖继承 `execution_status=executed`、旧 `decision/reason/evidence_ids`。`_judge` 约第 2015 行只选 `planned`，并把 `executed/failed` 纳入已消耗预算；新覆盖既跳过独立判断，又占用检查额度。这是程序结果状态错误，和模型速度、表达质量无关。

独立脚本直接调用生产方法，验证了：已执行模板会产生“新核对页却带着旧选择页结论”的项；新项不进入实际 `_judge` 输入；额度为 2 时，一条旧已执行项加一条错误继承项会挤掉一个真正待执行项。以原模板为 planned 的对照则正常进入 `_judge`。

### 额度口径及实现接口

A07 没有规定“所有重查免费”。当前 `_judge` 的普通检查额度按**本 run 内唯一 check_id**计数；`_reopen_gap_checks` 为同一覆盖补证设置 `reevaluation_requested` 后允许复评，仍受模型调用次数及补查轮次限制。该行为可保留为 D-COV-06 的验收口径：一次普通检查加一次合法复评，在唯一覆盖统计中仍为一项，在 judge 调用记录中明确为两次。新 run 按新 run 统计额度，旧 run 的记录保留；不能把新任务或新对象伪装成旧覆盖复评以规避额度。

B 可在 `_apply_check_plan` 写入新字段前对照原计划的任务、规范对象、来源版本、适用条件和必要证据，区分“同一计划”“补证复评”“实质变更”。复用现有 `_reopen_gap_checks`、会话变更事件和报告版本存储机制；不要把所有字段差异都机械视为新任务。实现后按 D-COV-01—06 逐项留档；这部分验收与已完成的新增覆盖 10 条回归分开统计。
