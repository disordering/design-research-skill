# D 测试判定说明

**版本：D 判定口径 v1.1｜冻结日期：2026-10-21｜用于后续新运行**

本版统一 R05、R18、G02 的判定顺序和证据记录，并统一修改建议的去重方式。其余条目沿用运行所绑定的判据。新运行记录本说明的版本及所用截图、原型、任务上下文和判据文件。

## 1. 版本与执行记录

既有三轮保留为 **D v1.0 结果**：24 条判据有 22 条三轮状态一致，一致率 **91.7%**；4 项设计目标有 3 项三轮状态一致，一致率 **75%**。原输出、原文件版本字段及上述统计均保留，不以 v1.1 回改。v1.1 的新运行单独统计，结论由新运行证据产生。

本说明依据三轮对照结论，以及第 1 轮冻结的判据、任务上下文、截图与原型；原始文件及哈希见证据索引。本文件是测试执行口径，不改写仓库正式判据；生效不依赖 A 或专家确认。

每项先记录证据，再选择状态。共同字段如下：

| 字段 | 填写要求 |
|---|---|
| `id`、`protocol_version` | 判据或子项编号；固定写 `D v1.1` |
| `evidence_source` | 文件路径和具体位置，例如截图左下属性栏、上下文字段；外部材料写名称和定位 |
| `visible_evidence` | 可见原文、控件状态或具体视觉关系；写观察，不写结论代替观察 |
| `known_context` | 已提供的用户、任务或交互事实，并关联来源 |
| `missing_evidence` | 尚缺的具体事实；没有则写“无” |
| `decision`、`reason` | 状态及其满足的判定条件 |
| `finding_id` | 存在可见问题时关联同一现象编号；其余为空 |

明确事实、推断和未知信息分别记录。模型对“常见手游用语”“玩家应该知道”的印象不作为用户熟悉度证据。四状态的中文标签固定为：`candidate_issue`＝候选问题，`no_visible_issue`＝未见问题，`insufficient_evidence`＝需补充信息，`not_applicable`＝本页不适用。

## 2. R05：关键文案避免未解释的内部术语

检查对象是非错误状态下、与主要任务有关的文案。先判断用户和任务，再判断术语；错误提示中的术语交由 R23 检查。

### 证据字段

除共同字段外，逐个候选术语填写：

- `term`、`location`：术语原文及位置。
- `target_user`、`expertise_evidence`：目标用户及其是否为该领域专家的依据。
- `term_meaning_source`：术语含义及来源，例如产品词表、任务说明或界面解释。
- `familiarity`、`familiarity_evidence`：熟悉／不熟悉／未知，以及对应目标用户的访谈、测试记录或明确提供的研究结论。词表能证明含义，不能单独证明熟悉度。
- `primary_task`、`task_source`：主要任务及其来源。
- `required_for_task`、`necessity_evidence`：必需／非必需／未知；说明不理解该词会阻碍哪一步。仅“出现在页面上”不等于必需。
- `visible_explanation`：截图中是否有清楚的就近解释，引用解释原文。

### 决策顺序

1. **排除明确不适用。** 没有相关的非错误关键任务文案，或已知目标用户为该领域专家，选 `not_applicable`。用户信息缺失本身不等于不适用。
2. **确认适用前提。** 目标用户是否为非专家、主要任务或关键文案范围无法确认，选 `insufficient_evidence`，写出缺项。
3. **检查任务必需性。** 对每个未解释的候选术语，确认完成主要任务是否必须理解。已证实非必需的术语不构成本条问题；必要性未知且会影响结论时，选 `insufficient_evidence`。
4. **检查理解依据。** 必需术语已有清楚的可见解释，或有目标用户熟悉该词的证据，可通过该术语检查。必需且未解释，并有依据确认其为目标用户不熟悉的内部术语，选 `candidate_issue`。含义或熟悉度未知时，选 `insufficient_evidence`。
5. **汇总。** 任一术语满足候选问题条件即选 `candidate_issue`；没有候选问题但存在影响结论的未知项，选 `insufficient_evidence`；适用且关键文案检查完整，没有上述问题，选 `no_visible_issue`。

### 正反例

- **正例／未见问题：** 非专家用户需要选择角色定位，界面就近写明“强攻：以直接伤害为主”；任务所需含义已有解释。另一种正例是已提供的目标用户测试记录能支持其理解该词。
- **反例／候选问题：** 任务要求非专家玩家按定位选择角色，产品词表确认“强攻”为内部类别，目标用户测试显示无法理解；界面只显示该词且没有解释。
- **证据不足：** 上下文只写“中轻度手游玩家”，截图显示“属性：雷电”“定位：强攻”。这不足以证明熟悉度；还需确认主要任务是否要求理解这些词。若任务必要性已确认而熟悉度未知，选需补充信息。
- **非必需与不适用的区别：** 若任务说明明确只需启动试用，且无需按属性或定位作选择，这两个词本身不触发 R05；仍应检查其他关键文案，再决定是否未见问题。若页面只有错误提示而无本条检查对象，则本页不适用。

## 3. R18：相关输入和可选项形成可识别的组

本条仅检查需要填写的字段，或需要选择的选项。纯展示内容的排布不纳入 R18。**纯展示型奖励卡，即使排列整齐、同属“奖励预览”，也选 `not_applicable`，不以分组清楚判为未见问题。**

### 证据字段

- `items`、`interaction_role`：逐项列出对象，标为输入字段／可选项／纯展示／未知。
- `interaction_evidence`：填写或选择能力的依据，例如可见复选框、选中状态、明确的选择说明或已提供的交互定义。卡片形状本身不证明可选。
- `group_relation`、`relation_source`：哪些项回答同一问题、哪些项不相关，以及依据。
- `group_cues`：组标题、间距、边界等具体线索。
- `mixing_evidence`：相关与不相关项目如何混排、由此产生哪一种归属歧义。

### 决策顺序

1. 确认是否存在多个相关输入或成组选项。已知只有纯展示卡、单个字段或单个选项，选 `not_applicable`。
2. 无法确认对象是否可输入／可选择，或无法确定项目间关系，选 `insufficient_evidence`。
3. 确认适用后，检查组标题、间距或边界。相关项与不相关项混杂，且可见地造成“哪些项属于同一问题”的歧义，选 `candidate_issue`。
4. 关系已知、相关区域可完整检查，且分组可辨，选 `no_visible_issue`；裁切或清晰度使分组无法判断，选 `insufficient_evidence`。

### 正反例

- **正例／未见问题：** “试用难度”的三个单选项置于同一标题下，与“奖励领取方式”的选项有明确间距。
- **反例／候选问题：** 已知难度与领取方式是两道不同问题，但选项混排于同一无标题区域，没有间距或边界提示其归属。
- **不适用：** 奖励预览仅展示钻石、道具及数量，不要求用户选择任何奖励。
- **证据不足：** 三张奖励卡是否可点击选择没有可见线索，也没有交互定义。先记录能力未知；不能用“看起来像卡片”判为可选项，也不能直接认定纯展示。

## 4. G02：三个子项分别判断，再汇总

G02 的目标包含主视觉焦点、主要信息可读、留白与密度。每个子项均使用 `met`（达到目标）、`observed_violation`（存在可见违反）、`insufficient_evidence`（证据不足）。逐项保存 `decision`、`reason` 和证据，不以其中一项代替全部目标。

| 子项 | 必填专项证据 | 正例：`met` | 反例：`observed_violation` |
|---|---|---|---|
| G02.1 主视觉焦点 | `focal_elements`：角色和核心按钮的位置；`competing_elements`：竞争元素；`hierarchy_evidence`：面积、对比、位置、遮挡的具体关系 | 角色展示及“开始试用”按钮形成清晰主层级，次要信息可辨但不掩盖它们 | 次要奖励板或装饰遮挡核心按钮，或以明显更强的视觉权重使核心入口难以定位 |
| G02.2 主要信息可读 | `key_information`：按任务列出应读文字与数值；`readable_text`：可辨原文；`readability_evidence`：字号、对比、背景、重叠或裁切的可见情况；`viewing_basis`：所用截图尺寸及查看方式 | 角色名、必要数值、奖励数量、任务按钮等主要信息完整、清楚可辨，背景不干扰识读 | 主要数值与纹理重叠、文字被切掉，或对比不足导致关键内容无法清楚辨认 |
| G02.3 留白与密度 | `regions`：检查区域；`spacing_evidence`：区域内外的间隔和分隔；`density_evidence`：装饰、文字、边框聚集的位置及影响 | 主要内容周围有可辨的净空或分隔，密集装饰未挤占阅读与操作区域，各信息区易于区分 | 纹理、框线和文字连续拥挤于主要内容周边，缺少可辨间隔，造成区域边界混淆或阅读、操作区域受挤压 |

留白指支持阅读和分隔的空间，不要求白色背景。配色鲜艳、元素数量多、存在纹理，均不能单独证明 G02.3 违反；必须指出具体区域及其拥挤或分隔失效的表现。角色醒目也不能替代 G02.2、G02.3 的检查。

### 决策顺序

1. 按任务与设计目标确认角色、核心按钮和主要信息清单，再定位三个子项的检查区域。
2. 对每个子项，先找具体可见违反：证据成立则记 `observed_violation`。没有可见违反且证据足够支持达到目标，记 `met`。缺少必要上下文、相关区域被裁切或分辨率不足以判断，记 `insufficient_evidence` 并注明缺项。
3. 汇总 `G02.overall_decision`，严格按以下顺序执行：

```text
任一子项为 observed_violation → overall_decision = observed_violation
否则，至少一项为 insufficient_evidence → overall_decision = insufficient_evidence
否则，三个子项全部为 met → overall_decision = met
```

例如：`met / met / observed_violation` 汇总为存在可见违反；`met / met / insufficient_evidence` 汇总为证据不足；只有 `met / met / met` 才达到目标。两个子项通过不抵消另一个子项的违反。

正反例用于说明状态条件，不是对下一轮截图的预先结论。装饰现象已写入 G03 或 G04 时，仍完整检查其是否同时违反 G02 的具体子项。

## 5. 多目标关联与修改建议去重

先按可见现象建立唯一 `finding_id`，再关联判据或目标。记录 `location`、`phenomenon`、`evidence`、`related_ids`、`suggestion`。

1. 同一位置、同一具体表现、同一修改动作的发现合并为一条；将所有受影响编号写入 `related_ids`。
2. 判据和目标仍分别按各自条件选状态；跨目标合并建议不改变各项状态。
3. 修改建议数按唯一 `finding_id` 统计。不同位置、不同问题机制或需要独立修改的发现分别计数。

**正例：** 奖励底板的密集纹理同时造成区域拥挤、底板喧宾夺主和无意义纹理堆叠，且各项均有对应证据，记为一个现象，关联 `G02.3、G03、G04`；“简化该底板纹理”只计一条修改建议。

**反例：** 同一奖励底板纹理问题分别写成三条建议并累计三次；或因为已归入 G04，直接跳过 G02.3。两种处理均不采用。

每轮输出同时报告逐项状态和去重后的建议数；判据／目标一致率继续按同一编号的状态比较，不用建议数量替代。
