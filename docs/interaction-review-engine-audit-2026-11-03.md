# 交互评审引擎代码审查与技术路线判断

日期：2026-11-03

审查对象：工作区当前的 `engine/session_*.py` 会话评审链、浏览器/MCP 动作适配、
逐屏技术审查、证据核验、覆盖矩阵、报告与会话事件。此次审查以工作区现状为准，
不仅看 README 和既有测试结论。

## 结论先行

当前引擎已经不只是“把截图和提示词发给模型”。它是一条有材料来源、证据对象、
状态/动作记录、确定性检查和可追溯报告的会话式评审链，能够有效承担：

- 设计材料与正式要求之间的静态对照；
- 多页面、多状态任务的范围登记和缺项检查；
- 在授权范围内实际点击/填写/滚动后，记录前后状态与路径；
- 把模型判断约束到当前证据、对象和检查编号；
- 对证据不足、未执行、工具失败和业务冲突保守地保留为未决；
- 生成人审版、审计版、机器可读版和新版复审报告。

但它还不能作为“交互方案是否合格”的最终裁判。更准确的定位是：
**证据可追溯的 AI 辅助交互评审 MVP**。它可发现静态设计问题、目标/要求差异和
部分运行路径问题；不能替代真实用户测试，也尚未用独立样本证明准确率、召回率和
跨场景稳定性。

## 从代码反推的技术路线

```text
链接/画板/原型/文档/图片
  -> AdapterHub 获取原始材料、截图、DOM/Figma 节点、动作结果
  -> Evidence + EvidenceObject + PageState + Transition
  -> 确定性视觉/结构指标与逐屏技术审查
  -> T03 模型提取评审任务、G/REQ、专家意见与材料冲突
  -> T04 按任务/页面/状态/对象展开检查计划和证据需求
  -> T05 模型提出单个动作，程序校验目标、授权、刷新状态并执行
  -> T06 分批判断；程序校验引用、必要证据类型、claim 和检查一致性
  -> T07 语义核验发现；可用独立模型，也可能回退主模型
  -> T08 会话事件触发补材料、业务决定和重查
  -> T09 人审/审计/JSON 报告和版本快照
  -> T10 对新版证据逐问题复审，不以漏报推断已修复
```

核心设计是“模型做语义，程序守边界”：

| 工作 | 模型 | 程序 |
| --- | --- | --- |
| 提取目标、要求、意见 | 语义理解与归纳 | 原文引用、材料角色、权威性和冲突规则校验 |
| 规划检查 | 判断适用性、对象和缺项 | 检查编号、证据 ID、对象 ID、覆盖单元和预算校验 |
| 运行交互 | 提议动作和目标 | 当前状态、观察控件、selector/坐标、授权、危险动作和前后变化校验 |
| 形成发现 | 解释现象、影响和建议 | evidence/claim/object 校验、动态行为需动作证据、E07 聚合并防止整体分掩盖子项 |
| 复审 | 比较新旧证据 | 必须引用当前版本、原来源和原对象；无新版证据保持未确定 |
| 报告 | 不直接改统计 | 由结构化会话生成人审、审计、JSON、阶段与原始响应索引 |

## 本次审查发现并修复的问题

### 1. 计划证据曾被当作已覆盖证据

状态覆盖、任务状态覆盖和状态图原先同时读取 `plan_evidence_ids` 与
`evidence_ids`。计划中“准备查看”的证据因此可能被统计为“实际检查过”，使覆盖数
和状态图偏乐观。

修复：覆盖只接受本次运行中 `execution_status=executed` 的检查所引用的实际证据；
逐屏审查仍可作为独立覆盖来源。新增“计划不等于执行”的回归用例。

### 2. 分支覆盖只做词重叠，容易把“点了保存”当成“保存成功”

原实现把动作文本与前后状态文本混在一起做 token 交集。动作目标命中“保存”，
就可能同时满足触发词和结果词，即使目标状态没有出现成功反馈。

修复：分支覆盖现在要求：

1. 存在已执行动作和观察到的状态迁移；
2. 触发词命中动作目标/理由；
3. 只检查目的状态证据；
4. 结果 token 覆盖达到阈值，并记录匹配迁移和分数。

新增“只有保存按钮、没有成功反馈”的反例。该规则仍属于确定性代理，不等同于
完整语义证明。

### 3. selector 点击缺少与声明目标的一致性核对

坐标点击原本会生成目标标记并交给视觉模型核对，但 selector 点击直接执行。
模型可能声明“取消”，实际给出“保存”的 selector；虽然危险动作授权仍会检查实际
DOM，目标语义并不一定一致。

修复：

- selector 必须来自当前状态已观察控件；
- 控件必须可用；
- 模型给出的 `target_label` 必须与实际控件标签一致；
- 执行前重新观察状态并再次校验；
- 实际目标写入 `observed_target`；
- 已执行动作保留原 action ID，便于证据链追踪。

同时把危险动作识别扩展到 `title`、`name`、`data-testid` 和 `value`，避免图标按钮
只写 title 时漏掉删除/提交等授权。

### 4. 动态 claim 仅在文字命中关键词时才强制动作证据

原先动态限制主要依赖“点击后无响应”等文本关键词。若文字较含蓄，但结构化 claim
已声明 `action_result`、`state_change` 或 `no_state_change`，程序可能漏掉动作
证据要求。

修复：`finding_requires_action_evidence` 同时检查结构化 claim 类型，确保动态声明
与文字表述走同一证据门槛。

## 有效性判断

### 已经具备的评审能力

- 能区分材料描述、设计标注、实现描述、实际观察、专家意见和用户决定；
- 能把目标/要求拆成可检查任务，并识别动态行为还需观察；
- 能检查跨页面状态、动作后的状态迁移和无效果点击；
- 能在证据不足时保留 `insufficient_evidence`，而不是用整体目标兜底；
- 能对同一问题维护历史、人工审核、业务决定和新版复审；
- 能输出可复核证据、原始响应、覆盖缺口和会话不变量。

### 当前不能直接宣称的能力

- **不能宣称完整可用性评估。** 没有真实用户行为、任务完成时间和主观负担数据。
- **不能宣称动态交互全覆盖。** 动作数量、时间、权限、页面路径和模型调用均有限制，
  未覆盖分支会被标为缺口，但探索策略本身仍可能漏掉重要路径。
- **不能宣称语义判断客观正确。** 分支结果、问题归因和严重度仍依赖模型解释；
  确定性检查主要防止证据越界和明显矛盾。
- **不能宣称独立验证。** 未配置独立 verifier 时，T07 由主模型自检；报告应保留
  `verifier_model_status`，不能把“已核验”理解为第三方真值。
- **不能把回归数量当效果成绩。** 220 项测试证明契约和控制流，不证明设计判断
  准确率、误报率或真人可用性。
- **不能自动裁决业务冲突。** 正式要求互相冲突时仍需用户给出有理由、有身份的
  业务决定，之后才能继续判断方案符合性。

## 验证结果

- 工作区 `python -m pytest -q`：**220 passed**；
- `python -m compileall -q engine`：通过；
- `git diff --check -- engine tests`：通过（仅有 Git 的换行提示）；
- 浏览器真实 Chromium 夹具覆盖：状态刷新、已观察 selector、目标不一致阻断、
  危险动作授权和标题型图标按钮；
- 原有坐标目标核对、无效果点击、部分观察、方法预算和材料接入回归保持通过。

## 建议的下一轮工作

1. 用独立标注集测“正确报出的问题 / 漏报 / 误报 / 覆盖缺口”，按场景分别统计，
   不用单案例结果替代。
2. 为分支覆盖补语义等价规则或第二模型核验，重点处理近义反馈和否定表述。
3. 把“本轮执行完整”与“方案评审结论充分”拆成两个显式字段，避免用户把
   `complete` 理解为方案合格。
4. 对同一任务记录必要的页面/状态集合，减少把所有捕获状态机械挂到所有任务造成的
   覆盖膨胀。
5. 建立真实交互方案的失败路径样本，重点测：返回、取消、保存失败、权限不足、
   空状态、重复提交和状态恢复。
