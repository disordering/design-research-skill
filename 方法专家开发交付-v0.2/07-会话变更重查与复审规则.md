# 第7步：会话、变更、重查与复审规则

版本：0.2-method-draft；设计规格，尚未接入B/C。延续第1—4步的会话状态并细化事件、影响分析和验收。用户问题不必等全流程结束才可提出。

## 1. 四类状态必须分开保存

| 对象 | 状态 | 含义 |
| --- | --- | --- |
| 会话 | created、reading、planning、checking、awaiting_input、rechecking、completed、cancelled | 本轮主要阶段 |
| 检查执行 | planned、running、executed、blocked、failed、not_executed；当前范围另记excluded | 是否真的进行检查，excluded不改写旧结果 |
| 模型判断 | R/E01—06四状态；G/REQ/E07三状态；E08冲突状态 | 本次证据下的结论 |
| 人工审核 | unreviewed、confirmed、rejected、needs_verification | 人的决定，与模型原值分开 |

会话额外记录pending_questions、pending_authorizations、active_phase、blocked_check_ids。局部等待且还有可做检查时会话仍为checking，显示等待事项；全部可执行工作都被阻断时才awaiting_input。等待不抹掉进度。

## 2. 会话状态转移

| 当前 | 事件/条件 | 下一状态 | 必须保存 |
| --- | --- | --- | --- |
| created | 至少一项入口/材料已登记 | reading | session_id、初始目标与来源 |
| reading | 已取得可评审材料 | planning | 成功/失败材料及原始证据 |
| reading | 全部材料不可取得 | awaiting_input | 失败类别、恢复方式 |
| planning | 有至少一个合法可执行检查 | checking | 检查计划、版本与适用理由 |
| planning | 无可执行项且需关键信息 | awaiting_input | 问题与受阻检查关联 |
| checking/rechecking | 只剩依赖用户/授权的工作 | awaiting_input | 所有局部结果与待答项 |
| awaiting_input | 补充可用材料/授权 | reading或planning | 更新事件；新增材料先reading，否则planning |
| checking | 补充导致计划失效 | rechecking | 变更事件、失效依赖与重查计划 |
| rechecking | 受影响检查完成 | checking或completed | 新判断；有剩余普通项则checking |
| reading/planning/checking/rechecking/awaiting_input | 用户要求结束或本轮无待执行项 | completed | 报告complete/partial、执行范围、未决项 |
| 任一活动状态 | 用户明确取消 | cancelled | 已完成快照；停止调度，不抹掉已有记录 |
| completed/cancelled | 用户明确继续/提交新版 | 新run的reading或planning | 原run不可改写，新run关联parent_run_id |

全局工具故障需要用户处理则awaiting_input；无法恢复且没有其他工作时输出partial并结束，不无限重试。若等待用户必须的信息，只继续不依赖该信息的检查，不能把沉默当确认。

## 3. 提问规则

先查材料，再问影响判断或执行的问题。每个问题记录question_id、已知事实、缺项、影响的check_ids、是否阻断、可接受答复类型、当前版本。每轮默认最多集中3个相关阻断问题；这是本项目交互设计值，不是通用标准。

优先级：访问/授权阻断 > 主任务与关键业务条件 > 材料冲突 > 非关键解释。能从已提供材料读取的不重复问；非关键缺项写未决并继续。用户选择暂不提供时不反复追问同一缺项，只有新证据改变问题才重开。

回答首先分类为事实补充、目标变更、材料更新、业务取舍、审核意见或无关说明。用户说明记录statement来源；业务取舍记录决定者和适用范围。它们不冒充运行观察。

用户可以否定模型意见；系统重查依据并说明维持/修改原因。不得为了迎合而盲从，也不得在证据已变化后机械复述。

## 4. 变更事件与影响规则

每次有意义变更创建event_id、parent_context_version、新context_version、来源、时间、旧新值、affected_ids和影响理由。记录actor_type区分human、ai、program；来源不明则unknown，不生成虚假人名。

| 事件 | 最小影响范围 | 需要重新取得什么 |
| --- | --- | --- |
| 修改目标用户 | 依赖用户熟悉度/必要性的R05、R16、R24及相关目标 | 用户依据；画面若没变可引用当前有效证据 |
| 修改主任务/终点 | 主操作、相关性、路径、目标与条件检查 | 重定计划，取新的相关路径证据 |
| 补奖励规则 | E06/E07/E08及依赖奖励解释的条目 | 带来源规则与必要操作结果 |
| 驳回一条发现 | 支持该发现的检查项及它们的依赖结论 | 核对原证据，必要时补取；不强制重跑所有材料 |
| 改严重度 | 影响说明和人工等级 | 默认不重跑视觉；如果理由带新事实则触发相关重查 |
| 更新页面/代码/原型 | 变更对象、关联转移、上下游任务和依赖该版本的结论 | 新版证据；旧快照不能证明新版 |
| 扩展/缩小范围 | 新增项、被排除项和汇总 | 被排除项保留历史，不自动变不适用 |
| 业务决定解决冲突 | E08及基于冲突要求的E06/E07和关联任务 | 记录决定；实现是否符合仍需证据 |

程序保存“材料/上下文事实 → 检查项 → 候选问题 → 报告”的依赖关系，递归找受影响项；AI补充语义影响并给理由。依赖关系不可靠时扩大到相关任务整条路径重查；无法确定受影响材料版本时禁止沿用旧结论并列未决。不会声称所有变更都能精确局部重查。

受影响旧结果标stale，仅作为历史。新run生成新check结果。重查完成后旧人工审核作为历史上下文，不直接复制成新问题已确认。

## 5. 异常、恢复与重复动作

| 情况 | 处理 |
| --- | --- |
| 读取超时/临时断连 | 保存当前证据，最多一次有条件的只读重试；仍失败记failed，给出范围限制 |
| 点击超时 | 先确认动作是否实际生效，不直接重复；有真实副作用风险则等待明确处理 |
| 登录失效/权限失败 | 保存访问阻断，不将工具故障算产品问题；请求用户恢复权限或改用静态材料 |
| 模型格式错误 | 程序验证后允许一次结构修复；仍错误保留原响应并记失败，不填造判断 |
| 模型证据引用错误 | 退回补证/重新判断；JSON合法不代表语义正确 |
| 浏览器刷新/进程中断 | 从快照恢复目标、版本、已完成检查、待答项和人工决定；running项改为interrupted记录，执行状态回planned/blocked并说明 |
| 恢复后外部页面已变化 | 核对版本/状态，必要时重新取证；不凭旧坐标继续操作 |
| 重复提交同一事件 | 用event_id/request_id去重；不得制造重复报告、重复真实操作或重复问题 |

completed是本轮交付状态。report_completeness=complete要求全部约定检查有可追溯处置，executed/明确不适用/有理由excluded；仍有blocked、failed、not_executed则partial。complete仍可有已检查后证据不足或待业务决定，必须另外显示“未决项数量”，不能写“全部验证通过”。

## 6. 修改后逐问题复审

旧问题作为稳定历史对象，生成recheck_id关联旧finding_id、新run、新方案版本、新证据和复审理由。匹配依据包括对象、位置/机制、任务和关联判据。同判据只产生候选关联，不证明同一问题。

| 复审状态 | 必需条件 |
| --- | --- |
| resolved 已解决 | 新版相关路径/状态在原触发条件下有证据，原问题不再成立 |
| partially_resolved 部分解决 | 明确哪些已改好、哪些仍存在，两侧都有新版证据 |
| persists 仍存在 | 新版在可比条件下仍满足原触发条件 |
| cannot_determine 无法判断 | 缺新版相关证据、条件不可比或未执行，写明缺项 |
| not_applicable 不再适用 | 新需求/范围/功能改变使原条件不成立，提供来源；不计修复 |
| manually_excluded 人工排除 | 人工决定不处理并给理由；不计修复 |

模型可提出上述候选状态，review_status默认unreviewed。只有有身份/时间/理由的人工记录才能显示“人工已确认”。原有静态问题可用新版静态证据复审；原动态问题需新版对应动态证据，不能用单张截图证明已修好。

旧报告没再出现该发现 → 先cannot_determine，直至针对性复查。冲突被裁决 → 要求已确定，不能直接记实现问题已解决。修复率只对预先定义的可比问题集合统计，人工排除/不再适用不计分子。

## 7. 完整事件示例（合成，非实测）

run-01误以为奖励需手动领取，形成缺入口候选。用户说明“自动发放”，系统保存statement与event-01，创建context-v2，标记E06/E07及依赖发现过期。run-02重新判断：若手动领取假设无依据，撤回该候选并保留撤回原因；另检查实际结果是否说明发放状态，到账仍无证据则待验证。用户上传新版后生成run-03，不覆盖run-01/02。新报告没有该问题不能自动填resolved，需新版相关证据。

## 8. B/C必须落地的行为

会话恢复、事件去重、依赖失效、局部重查/保守扩大范围、旧新报告分离、模型与人工分离、异议导致真实重查、复审证据必填。仅增加聊天框或改scenario文案不构成上述功能完成。
